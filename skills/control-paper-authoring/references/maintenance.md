# 模块维护与领域扩展

仅在修改技能、接入提供者、添加领域或查看历史时读取。普通论文写作不加载维护记录。

## 文件职责

- `SKILL.md`：任务边界、M01–M08 的职责与触发条件，不保存领域规则副本。
- `profiles/index.md`：已存在的领域配置及适用范围。
- `profiles/<领域>.md`：该领域的模块绑定及明确的适配关系。
- `modules/` 和配套技能：各模块的实际规则与按需资源。
- `CHANGELOG.md`：按日期记录实际行为变化、原因、涉及模块及验证范围。
- 来源记录：保留作者、文献和阅读范围，与日常规则分离。

模块是可独立修改的职责，不要求每个模块都包装成新技能。已有 skill 能承担职责时直接引用；需要学术或领域适配时用短的模块文件说明差异，避免复制全文。

## 接入新 skill

1. 读取新 skill 及其真实依赖，确认它改变哪项决策。明确是替换某模块的主要规则，还是补充某个特定场景；无关能力不合并。
2. 在目标领域配置中登记模块、角色（主规则或条件扩展）、真实路径、触发条件、适用语言、输入与输出、与已有规则的关系。路径相对于配置文件，不能写某台电脑的盘符路径。
3. 复用现有规则，不将同义指令再粘贴到主入口。替换时迁移原模块独有且仍适用的要求，更新调用方；保留引用论文的来源和第三方许可。
4. 检查事实、范围、术语、标点、章节和交付要求。已由用户明确决定的冲突沿用该决定；新的取舍冲突先列原文及影响、询问用户，独立部分继续。不能用“最后加载者优先”。
5. 核对引用可达、依赖可用、配置闭合、无自调用循环，以及不受本次变更影响的领域配置。至少走查一个本模块场景和一个不应触发它的场景。
6. 更新日志、相应中英文说明，并在已授权范围内同步安装版、分发包和远端。只记录实际检查，不把结构校验称为写作效果验证。

新 skill 的接入记录可采用以下字段，不需要新增可执行调度程序：

```text
模块：Mxx
角色：主规则 / 条件扩展
提供者：相对于本配置的实际 SKILL.md 路径
触发：具体任务与语言
输入：现有材料及必须保留项
输出：正文 / 文件修改 / 供后续模块使用的结果
适配：补充或替换哪些现有规则；不适用的第三方规则及原因
缺失处理：说明缺失，继续不依赖它的部分；不自动安装
```

每个模块只保留一个主规则提供者。扩展只在声明的场景读取，须先完成冲突核对；未登记的文件不因放进目录就自动生效。

## 增加其他领域

新建领域配置，显式绑定全部 M01–M08，并登记到索引。可以复用 M02、M03，也可以按该领域需要替换；章节、句式、词汇、证据、实验和交付分别选择适合的提供者。不修改 control 配置来假装切换领域，不自动继承未列出的控制规则。只针对新领域的定制放进新提供者或适配器；不要改共享模块后让旧领域被动改变。确需改共享规则时，明确影响范围并核对每个使用者。

模块请求另一职责时使用“当前领域的 Mxx”，由当前配置解析。指向自身示例、来源和辅助文件的相对链接仍可使用；不要把跨模块调用硬连到控制领域实现。对外部 skill 内部的固定依赖也要审查，必要时写适配器或选另一提供者。

例如，未来为某领域提供新的词汇 skill 时，可在它的配置中将 M05 指向该 skill，其他模块沿用明确选定的提供者。若新知识也改变证据标准，则同时调整该领域的 M06；不能假定词汇替换本身已完成领域适配。未创建的配置只是扩展方案，不列为已有能力。

## 日志约定

每次实际变更追加日期、模块/配置、改变的行为、原因或用户确认、受影响路径、验证和同步结果。新决定明确替代哪条旧决定；日志中的旧规则只作历史，不自动参与写作。不要记录未提供的批准、未执行的验证或未公开的论文内容。

历史重复说明无需常驻运行规则。必要案例由对应模块保留，迁移关系放审计记录，旧全文通过版本历史追溯。
